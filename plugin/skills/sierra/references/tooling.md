# Sierra Tooling

How data enters the session. The download commands and the on-disk layout are in
`.composer/docs/agent-traces-reference.md` in the agent directory, regenerated by the CLI on every
pull; the bundled `debug-conversations` and `debug-simulations` skills walk the same layout. Two
things that doc does not say: run the command from the agent directory with the full-domain
target after `ghostwriter`, such as `bbva.sierra.ai/default`, because a non-interactive shell
stops with «Multiple workspaces match» as soon as the agent has more than one workspace; and pass
ids in batches of about 20, since a 40-id batch returned without downloading anything.

MCP calls go directly from the main conversation. The server's note about delegating large
responses to a subagent is about payload size: an issue is about 2 KB and a conversation about
25 KB, and a subagent turns a two-second call into a minute or more. Simulation results come from
disk, never from `get_test_results`.

`<base>` below is the skill's base directory, printed when the skill loads.

## Issues

`get_issue_details`, directly. The linked conversation ids come back in the `audit-` form the sync
needs.

## Conversations

The id is the `audit-` form from the issue or from `get_conversation_details`; the bare ULID in a
Studio URL returns HTTP 400 «invalid conversation id» (`docs/url-reference.md` has the mapping).

Read with `python3 <base>/scripts/runset.py conv <id>`. The download is the runtime's record: what
the model was shown, answered, called and which observations fired. `get_conversation_details` is
Studio's record of the same call: release, ids, custom fields, duration. The release hash exists
only there; `summary.json` has an empty `release_target`.

## Simulation runs

Read with `python3 <base>/scripts/runset.py`; `--help` lists the views. Write a parser only for what
the views do not cover: request and response bodies and timing in `traces/*.trace`, tool arguments
and results, comparisons across run ids. When a parser turns out reusable, add it to `runset.py` as
a view. Trace layout and debug.log event types: `.composer/docs/agent-traces-reference.md` in the
agent directory, regenerated by the CLI. Read it before writing a parser.

## Studio content

When `pnpm sierra ghostwriter pull` stops with «waiting for conflict resolution», an unfinished
rebase sits in `.composer/.git`. Report the conflicted files and stop; `pull --continue` or
`pull --abort` is Stan's call.

Read with `python3 <base>/scripts/blocks.py`; `--help` lists the columns.

- Which block says X: `blocks.py | grep -i "x" | cut -f1,2`. The path is the answer.
- An item named by its opening words: `grep -P '\tNunca ofrezcas'`.
- What reveals an item: `grep '› si'`, or `grep 'rootStore:<key>'` for a store flag.
- Did an edit land, does default differ from the workspace: save the outline before the pull or
  upload and `diff` after. Git shows it only where `.composer` is tracked.
- Editing: take the pointer from the line and change the JSON on the exact string. The outline is
  read-only.

The outline covers `.composer` only. Agent Code `description` and `instructions` strings, knowledge
articles and the platform base prompts are separate surfaces; a question about «anything in context
about…» searches those too.
