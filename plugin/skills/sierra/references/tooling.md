# Sierra Tooling

How data enters the session. The download commands and the on-disk layout are in
`.composer/docs/agent-traces-reference.md` in the agent directory, regenerated by the CLI on every
pull; the bundled `debug-conversations` and `debug-simulations` skills walk the same layout, at
`<agent-dir>/.composer/.claude/skills/<name>/SKILL.md`. Two
things that doc does not say: run the command from the agent directory with the full-domain
target after `ghostwriter`, such as `bbva.sierra.ai/default`, because a non-interactive shell
stops with «Multiple workspaces match» as soon as the agent has more than one workspace; and pass
ids in batches of about 20, since a 40-id batch returned without downloading anything.

MCP calls go directly from the main conversation. The server's note about delegating large
responses to a subagent is about payload size: an issue is about 2 KB and a conversation about
25 KB, and a subagent turns a two-second call into a minute or more. Simulation results come from
disk, never from `get_test_results`.

`<base>` below is the skill's base directory, printed when the skill loads.

## Issues

An issue's data lives in the pages dir ([info.md](./info.md)) at `agents/<agent>/issues/<n>.json`: the
`get_issue_details` response with its default arguments, saved verbatim, so comments and linked
calls without conversation transcripts. Read it before calling the tracker. Every call you do
make, because the file is missing or because something changed the issue, a comment, a status,
ends with its response written there untouched. The linked conversation ids come back in the
`audit-` form the sync needs.

## Conversations

The id is the `audit-` form from the issue or from `get_conversation_details`; the bare ULID in a
Studio URL returns HTTP 400 «invalid conversation id» (`docs/url-reference.md` has the mapping).

A call the skill has read lives in the pages dir next to its issue, at
`agents/<agent>/conversations/<audit-id>/`: the ghostwriter download as the CLI wrote it
(`debug.log`, `summary.json`, `traces/`) plus `details.json`, the `get_conversation_details`
response saved verbatim. The issue file's `linkedLogs[].id` is the folder name, so the issue leads
to its calls and nothing else indexes them. Look there first. When the folder is missing, take the
download from the agent directory's `.composer/conversations/<audit-id>/`, and when that is missing
too, download it (command in `agent-traces-reference.md`); either way copy the folder into the
pages dir before reading it. Every `get_conversation_details` call you make ends with its response
written to that folder's `details.json`, untouched.

Read with `python3 <base>/scripts/runset.py conv <id>`; it looks in the pages dir before the
`.composer` directories. The download is the runtime's record: what the model was shown, answered,
called and which observations fired. `details.json` is Studio's record of the same call: release,
ids, custom fields, duration. The release hash exists only there; `summary.json` has an empty
`release_target`.

## Step outputs

**SOP.** An agent's SOP, BBVA's functional document, lives as markdown at `agents/<agent>/sop/sop.md` in the pages dir (`pandoc <file>.docx -t gfm --wrap=none -o sop.md`, cover images and empty headings stripped); the analysis brief carries it whole when it is there. Hipotecarios has it since 22/09.

**Issue setup.** Before any step runs, the issue gets its own checkout and Studio workspace: `scripts/setup.py <agent> <n> --pages <dir> --repo <repo>` (the card's branch button) makes the linked worktree `<repo>/.claude/worktrees/<prefix>-<n>` on branch `stan/<prefix>-<n>` off the main checkout's HEAD (prefix cob, opp or hip), shares main's skills and `.targets`, installs the agent's node_modules, connects or creates the Studio workspace `<prefix>-<n>` and binds Ghostwriter to it with the tree's content pushed. Status in `agents/<agent>/cards/<n>/setup/status.json`; the run and chat routes refuse until it says done, and then run in that worktree. Uncommitted edits of the main checkout are not in the worktree.


The JSON a workflow step skill returns for an issue is saved in the pages dir next to the issue, one file per step:
`agents/<agent>/cards/<n>/analysis/answer.json` from `issue-analysis`, `agents/<agent>/cards/<n>/strategy/answer.json`
from `sim-strategy`, `agents/<agent>/cards/<n>/context/answer.json` from `context-edit`.
`python3 <base>/scripts/card.py ia <agent> <n>` renders the Issue Analysis section from the first into the card.
`python3 <base>/scripts/run.py <agent> <n> [analysis|strategy]` does one step headless: the step's brief (`brief.py
--step`), pi on the skill text with its schema (json mode, prompt on stdin, read and bash tools), the previous answer
and card copied to `<step>/history/`, the new JSON written and rendered. The strategy brief carries the agent's
simulation files, the tags its source declares, the issue, the Issue Analysis answer and the linked call; it fails
until the analysis answer exists. Progress is `<step>/<n>.status.json`; the play buttons in the card's Issue Analysis
and Sim Strategy headers start the same runs through the pages server and the page re-renders the card when they land.
The context-edit step runs the same way (`context`, header Studio Context Edit). The resolution step is interactive: the
pages server keeps one pi session in RPC mode per issue (`agents/<agent>/cards/<n>/resolve/runs/`), opened from the Resolution
header with the `resolve` brief as its first message; the session drawer streams its events and takes messages, steers
while the agent runs, follow-ups, interrupts and answers to an extension's confirm or select.

## Simulation runs

`<sierra>` is the CLI in the agent directory, `<agent-dir>/node_modules/.bin/sierra`; `<workspace>` the workspace
the work runs against, an issue's own from the pages dir's setup step, else the name from `.targets/`; `<runs>` a
folder for the run's files; `<scripts>` this skill's scripts directory. Launch:

```
<sierra> -C <agent-dir> test <workspace> --names "<name or id>" --num-runs 5 --json -y --run-id-file <runs>/run-id > <runs>/run.json
```

- `<workspace>` is the only workspace you may name: `sierra test` first uploads the checkout's simulation
  definitions to the whole agent, then runs against the workspace named. Never `default`, never another name,
  never `--simulate-speech`.
- `--num-runs` is 3 for a probe, 5 for a verdict; the platform's limit is 5.
- The launch takes a few minutes and returns when the platform is done. Wait for it.

Read:

```
python3 <scripts>/runset.py summary <runs>/run.json [--vs <baseline>.json]
```

`summary` prints per sim passed/total, the judge lines and the run ids from that file; more files add up. When
it prints 0/n with no judge line seconds after the launch, the platform is still running and that file will not
change: wait two minutes, download the run as below and read `runset.py <run-id>`; repeat until every result is
there. Transcripts come only from the download:

```
<sierra> -C <agent-dir> ghostwriter bbva.sierra.ai/<workspace> --download-simulations --run-id $(cat <runs>/run-id)
python3 <scripts>/runset.py $(cat <runs>/run-id)
python3 <scripts>/runset.py $(cat <runs>/run-id) --failed
python3 <scripts>/runset.py $(cat <runs>/run-id) --transcript <result id, test id or name substring>
```

Run runset.py from the checkout, where it finds the agent's `.composer/`; `--help` lists the views. Write a
parser only for what the views do not cover: request and response bodies and timing in `traces/*.trace`, tool
arguments and results, comparisons across run ids. When a parser turns out reusable, add it to `runset.py` as
a view. Trace layout and debug.log event types: `.composer/docs/agent-traces-reference.md` in the
agent directory, regenerated by the CLI. Read it before writing a parser.

## Studio content

When `pnpm sierra ghostwriter pull` stops with «waiting for conflict resolution», an unfinished
rebase sits in `.composer/.git`. Report the conflicted files and stop; `pull --continue` or
`pull --abort` is Stan's call.

Read with `python3 <base>/scripts/blocks.py`; `--help` lists the columns.

- Which block says X: `blocks.py | grep -i "x" | cut -f1,2`. The path is the answer.
- An item named by its opening words: `grep -P '\tNunca ofrezcas'`.
- What reveals an item: `grep '› si'`, or `grep 'rootStore:<key>'` for a store flag.
- Did an edit land, does default differ from the workspace: save the outline before the pull or
  upload and `diff` after. Git shows it only where `.composer` is tracked.
- Editing: take the pointer from the line and change the JSON on the exact string. The outline is
  read-only.

An edit reaches the agent only once it is pushed to `<workspace>`, the issue's own workspace, the one
Ghostwriter in the issue's worktree is bound to. Never push to another. The context step pushes its edit without a
go; everywhere else, push only with Stan's go:

```
python3 <scripts>/pull.py <agent> <checkout>
  (edit the block files; copy each edited file to <runs>/intended/)
<sierra> -C <agent-dir> ghostwriter lint
<sierra> -C <agent-dir> ghostwriter push
python3 <scripts>/pull.py <agent> <checkout>
diff <runs>/intended/<file> <agent-dir>/.composer/blocks/<file>
```

pull.py is `ghostwriter pull` plus one commit: the files a pull brings in at a version main has had are main's merges
reaching the workspace, committed as base; everything else stays uncommitted, the card's work.

- Pull right before editing: `pull` overwrites the local block files, and Stan edits Studio between
  turns.
- Push right after lint. A simulation run between pull and push makes the push fail with «updated
  simulation tests»: pull, re-apply, push.
- The diff after the second pull must be empty for every edited file, the whole file, not only the
  edited items: a merge push once came back with two other items of the same block reverted. When it
  is not empty, re-apply and push again before any run; a run before that tests the old content.
- A block file deleted locally deletes that block on push.

The outline covers `.composer` only. Agent Code `description` and `instructions` strings, knowledge
articles and the platform base prompts are separate surfaces; a question about «anything in context
about…» searches those too.
